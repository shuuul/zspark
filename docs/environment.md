# Environment variables

Every `ZSPARK_*` variable the tree reads, in one place. A variable that is added, renamed or removed changes its
row here in the same commit; the code's comment says how a switch works, this file says that it exists.

Nothing here is a setting a deployment needs: `zspark` runs with none of them set. What a client or an operator
chooses is a command-line option (`zspark` with no arguments prints them).

`zspark stack` reads no `ZSPARK_*` variable: its choices are flags (`--mps`, `--peer`, `--port`, ...). It sets
`CUDA_MPS_PIPE_DIRECTORY` and `CUDA_MPS_LOG_DIRECTORY` on its children, and `CUDA_MPS_ACTIVE_THREAD_PERCENTAGE` and
`CUDA_MPS_CLIENT_PRIORITY=1` on the small models' alone, never in a shell it did not start.

`./start.sh` and `./stop.sh` put that command in the background: `zspark.local.sh` at the root, copied
from `zspark.local.example.sh` and never tracked, holds the flags in its `STACK_ARGS`; the same file or the
environment names `ZSPARK_BIN` (the binary, `./zig-out/bin/zspark` unset), `LOG_DIR` (one `stack-*.log` a start,
`~/.cache/zspark/logs`), a per-checkout `STATE_DIR` (pid, recorded argv and the serialization lock,
`~/.cache/zspark/stack-CKSUM` of this tree's path), `STOP_S` (stop.sh's wait, 120) and `DRY_RUN` (1 prints and
changes nothing). The pid record keeps the process's /proc start tick: `stop.sh` signals it only while the
tick and this tree's `zspark stack` argv still match.

## Switches of the program

A run prints what it took of them on stderr, a line (`zspark: switches: NAME="value" ...` or `none`, paths left out): the
proof of a comparison's side. A value in quotes that holds other names is a shell that did not split a variable.

Read once by `zig/src/main.zig` before the command runs, so they reach `generate`, `chat` and `serve` and no
test (a test sets the variable the switch writes). Each is the base of a comparison or a diagnostic. A value
that does not parse as a number is 0.

## The host's

Variables the vendored TensorFold host reads. The host's `cli.zig` `env` lists them all; the
table below is the serving path's part, checked against it in `zig/tests/server/command_test.zig`
(`serve_env_inventory`). A name not listed is read by upstream's own main or engines and reaches nothing in
`zspark serve`; `TENSORFOLD_WIRE` and `TENSORFOLD_TOOL_GRAMMAR` are the exceptions upstream forgot to list, and
the `TENSORFOLD_PREFILL_*` names are guarded: one that states what is untrue of this build refuses startup by
name (`engine_api.prefill_env`).

| Variable | Value | Unset | What it does | Where |
| --- | --- | --- | --- | --- |
| `TENSORFOLD_API_KEY` | key text | open | The API key `--api-key` stands in for when it is not given; set, every route but `GET /health` asks for it (upstream's `auth.zig`) | the vendored `auth.zig`, `serve.zig` |
| `TENSORFOLD_NO_LIVE` | anything | live lines on | Hides the live status lines a TTY would get (`live.wanted`) | the vendored `live.zig`, `serve.zig` |
| `TENSORFOLD_SEED_SALT` | text | none | Mixed into the request seeds drawn fresh (a `--prompt-seed` request's is the prompt's alone) | the vendored `cli.zig`, `seed.zig` |
| `TENSORFOLD_REQUEST_LOG` | path | off | The request log's file (`--log-requests` names what it holds) | the vendored `serve.zig` |
| `TENSORFOLD_WIRE` | `spark`, `native`/`tensorfold` | the family's | Whether replies carry the Spark runtime keys (`prompt`, `ttft_s`, `prefill_s`, `decode_s`, `drafted`, `accepted`) or TensorFold's own; any other value refuses startup (upstream 1.2.7, `spark_wire.zig`) | the vendored `serve.zig` |
| `TENSORFOLD_TOOL_GRAMMAR`, `TF_DSV41_TOOL_GRAMMAR` | `1` | off | Every auto tool-call request is held to strict tools, as the grammar engine serves them (the second name is the pre-1.2.7 one) | the vendored `tool_grammar.zig` |
| `TENSORFOLD_SEED_SALT` | integer | none | Mixed into the request seeds drawn fresh (a bad value refuses startup; a `--prompt-seed` request's seed is the prompt's alone) | the vendored `serve.zig` |
| `TENSORFOLD_REQUEST_LOG` | path | off | Each chat and completion body appended as one JSON line, images redacted, for replays | the vendored `request_log.zig`, `serve.zig` |
| `TENSORFOLD_TOOL_ID_KEY_FILE` | path | random key | A stable key for the reply's tool-call ids (upstream 1.2.7). The `TENSORFOLD_PREFILL_*` names are guarded: one that states what is untrue of this build refuses startup by its name (`engine_api.prefill_env`). The family tuning rules `platform/environment.zig` registers (`TF_DSV41_*`, `TF_GLM_*`, `TF_SLIDE_*`, `TENSORFOLD_PREFIX_WAIT_MS`, `TENSORFOLD_PRESSURE_CACHE_PERCENT`, `TENSORFOLD_RESTORE_PREFETCH_*`, `TF_STARTUP_RECEIPT`, `TENSORFOLD_VIDEO_TOKENS`, `TENSORFOLD_PROMPT_CACHE_KEEP_OTHERS`) reach only upstream's own engines and main; zspark's serving path reads none of them.

## Machine-local network settings

Copy `.env.local.example` to `.env.local` in the repository root. The launch wrappers, checks, two-Spark tools and reference benchmarks load it automatically. Set `PEER` to the other Spark's direct-link address on each machine. `PEER_REPO` names its checkout when the path differs. `MODEL_LAN_HOST` and `MODEL_LAN_PORT` identify the live model listener for benchmark guards. The `SPARKDASH_*`, `SPARK_SSH` and `SPARK_SOURCE` settings are optional.

Use literal `KEY=value` lines with absolute paths. Explicit command-line arguments and exported variables take precedence over these defaults. `.env.local` is ignored by Git. Stack arguments still belong in `zspark.local.sh`, which can reference `$PEER` from `.env.local`.
